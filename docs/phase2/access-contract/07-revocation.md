# Session revocation

This section defines which sessions become unusable after an account security change. A session belongs to one account and is usable only while that account is active, `revoked_at` is null, and the current time is before `expires_at`, as defined in [accounts and sessions](01-accounts-and-sessions.md#sessions). The [PRD security and privacy requirements](../../prd.md#security-and-privacy) require revocation after password changes, role changes, and deactivation.

| Successful change | Sessions to revoke | Scope rule |
| --- | --- | --- |
| Password change or reset | Sessions belonging to the account whose password changed. | For a web-submitted password change or reset, preserve the current session only if it is a valid existing session belonging to the target account. A reset token does not itself exempt a session. If the web request has no valid existing target-account session, revoke all target-account sessions. CLI reset revokes all target-account sessions. This covers [web reset](../tickets.md#p2-31a-revoke-other-sessions-on-password-change-99) and [CLI reset](../tickets.md#p2-33-cli-administrator-password-reset-104). |
| Role change | All sessions belonging to the account whose role flags actually changed, including the initiating session if the actor changes their own roles. | The target account's sessions are revoked whether the actor changes another account or their own. Granting or removing either role counts as a change; submitting the same role flags is a no-op. See [role assignment](../tickets.md#p2-39a-role-assignment-route-115) and [role-change revocation](../tickets.md#p2-39b-revoke-sessions-on-role-change-116). |
| Deactivation | All sessions belonging to the deactivated account. | Revoke every target session, including the request's current session if the actor deactivates their own account. Deactivation removes the account's ability to use sessions, and past content attribution remains attached to the account ID. See [deactivation](../tickets.md#p2-40a-account-deactivation-route-118) and [deactivation revocation](../tickets.md#p2-40b-revoke-sessions-on-deactivation-119). |

The actor and target are distinct concepts. Revocation always follows the target account named in the successful change, not the administrator who submitted it. When the actor changes another account, the actor's sessions are unaffected. The current-session exception applies only to a web password update, including a reset flow, when the request also has a valid existing session for the target account. An actor's session for a different account never qualifies, and possession of a reset token alone never qualifies. Role changes and deactivation have no current-session exception.

If a role or deactivation request would remove the site's last active administrator, reject the account change and revoke no sessions. The same applies to validation errors, persistence failures, and requests that make no change. A request counts as successful only after the account change and every required revocation are durable. The system must not leave a changed password, role set, or account state paired with sessions that the change required it to revoke, and must not report success if revocation fails. This follows the [last-active-administrator rule](../../prd.md#functional-requirements) and the [Phase 1 write contract](../../phase1/content-contract.md#7-repository-operations), where failed writes leave no partial state.

Examples:

- A password reset submitted with a valid reset token and no valid target-account session revokes every session for that account. If a valid target-account session is also present on a web password change or reset, preserve that session and revoke all other target sessions; the reset token itself grants no exception.
- Administrator A changes account B from editor to administrator. B's sessions are revoked; A's sessions remain. If A changes A's own roles, all of A's sessions are revoked, including the one used for the request.
- Deactivating account B revokes all of B's sessions. If B is the last active administrator, the request fails and none of B's sessions are revoked.

This is a contract for later implementation. It does not set session lifetime, cookie or token behavior, CSRF handling, or audit-event details; those belong to their own access and audit sections.
