# Phase 3 ticket draft: configurable content and the publishing journey

Status: Draft written 2026-09-30 while Phase 1 and Phase 2 are still in progress. Planning does not wait for them: this doc is the ticket source for the `analyze-ticket` skill, which splits or refines `P3-nn` entries in place. GitHub issues are opened from the settled layout and target the `phase-3` integration branch; issue numbers are recorded here when opened.

Source: [work plan Phase 3](../work_plan.md#phase-3-build-configurable-content-and-the-publishing-journey), [PRD](../prd.md) FR-03, FR-04 (basic editing), FR-05, FR-06, FR-08, FR-13, FR-14 and the editorial consistency requirements. The [phase 1 content contract](../phase1/content-contract.md) section 10 and the [storage and deployment ADR](../adr/0001-runtime-content-and-deployment.md) fix the rules these tickets must follow.

Outcome for the phase: an administrator defines content in the interface, and an editor creates, finds, previews and publishes it without code changes. All five launch types render through the barebones public theme.

Each ticket has one entry point (admin HTTP route, public route, package API or document), one storage concern and one observable result. Ticket order follows the plan's four tracer bullets. Tickets are sized so a small model agent can take each one in a single test-first pass.

Not in this phase: images and documents (phase 4), menus, redirects, path changes, Trash and permanent deletion (phase 5), configuration deploy and diff commands (phase 6). Where a phase 3 screen would need one of these, it shows the phase 1 `path_change_unsupported` style error or omits the control.

## Contracts (start of phase)

Contract tickets write one section file each under `docs/phase3/` and add one link to the matching index, so they can run in parallel. No code.

Keep the phase 1 ID rules and reserved `title` and `path`. State the v1-to-v2 upgrade rule for an existing Page site: a v1 document is a valid v2 document with one type and no groups.

**Guidance**

The index gets one table row per section: `document.md` linked; `fields.md` (P3-01b), `validation.md` (P3-01c) and `changes.md` (P3-01d) listed unlinked as "planned", since each later ticket adds its own link (work plan rule 3). Edit nothing else; no code, no files under `docs/phase3/examples/` (P3-08 owns fixtures), no edits to `docs/phase1/`.
- Sources to cite, not restate: [page-config-v1.md](../phase1/page-config-v1.md) (ID grammar, reserved IDs, closed shape), [config-validation.md](../phase1/config-validation.md) (first-error walk, JSON path syntax, error classes and exits, canonical export bytes), [content-contract.md](../phase1/content-contract.md) sections 4 and 8 (the separate version markers, startup checks) and the [ADR](../adr/0001-runtime-content-and-deployment.md) (deploy-only production).
- Root shape: exactly `format_version` (JSON integer `2`) and `content_types`, in that schema order. `content_types` is a nonempty array; an empty array is `invalid_value` at `$.content_types`, exit 3. Any integer other than 1 or 2 is `unsupported_version`, exit 4, classified before the rest of the document as in phase 1.
- Type object: exactly `id`, `label`, `plural_label`, `fields`, `groups`, in that schema order (this order drives both the first-error walk and canonical export). `id` uses the phase 1 grammar `[a-z][a-z0-9_]{0,63}`; `label` and `plural_label` are strings (empty allowed, as for phase 1 labels); `fields` and `groups` are required arrays that may be empty. Element shapes are defined by P3-01b; this section links to `fields.md` by name only.
- ID rules: type IDs are unique across the document (`duplicate_id` at `$.content_types[N].id`, reported on the later occurrence); no type ID is reserved or mandatory, so `page` is only the default created by `init`. `title` and `path` stay reserved as field IDs within every type; field IDs are unique per type and may repeat across types. `unsupported_content_type` is not raised for v2 documents; it remains the v1 rule. Reuse the phase 1 error classes, paths and exit codes; add no new class.
- v1-to-v2 upgrade: the v2 reader accepts a `format_version: 1` document, validates it with the phase 1 rules, then maps it in memory to v2: `format_version` becomes 2, the one `page` type gains `groups: []` and a `plural_label` (see open decision below), and each v1 field becomes a v2 field that is ungrouped, single-valued and has no validation beyond its kind (P3-01b must define its new field properties so these are their defaults). No field ID, label, help text, required state or order changes, and no item or snapshot row is touched. The stored `active_config.document` and `site.config_format_version` stay 1 until the next configuration write stores the v2 form (P3-09); `serve` accepts stored format 1 and 2 and still rejects others with exit 4.
- Examples: include two inline JSON blocks, the upgraded default Page (from `internal/config/default.json`) and a two-type document (`page` plus one more type with one `short_text` field). Use only field properties known today plus a marked note that P3-01b adds the rest; each block must parse with `python3 -m json.tool`.
- Acceptance: `bash scripts/test` stays green; every link in both new files resolves; the section states the root shape, type shape, ID rules, error mapping, the upgrade rule and the version markers; a reviewer can derive P3-08's v2 parser tests without further design.
- **Open decision:** type ordering. The ticket calls `content_types` an ordered list, but phase 1 canonical export sorts `content_types` by ID ([config-validation.md](../phase1/config-validation.md#deterministic-export)), which discards array order. Choose one: array order is display order and canonical export preserves it (changes the phase 1 rule for v2); types carry no order and export keeps sorting by ID; or types gain an `order` property like fields. Blocks this ticket.
- **Open decision:** the `plural_label` given to an upgraded v1 type, which the admin sees in list headings. Candidates: copy `label` unchanged (deterministic, invents no text; administrators relabel later) or a fixed `Pages` when the v1 label is exactly `Page`. Blocks this ticket.

Write the `fields` section: every field property (`id`, `kind`, `label`, `help_text`, `required`, `order`, `group`, `multiple`, `validation`), which kinds allow `multiple`, and the group object (`id`, `label`, `order`). Groups only affect form layout; values stay keyed by field ID.

**Guidance**

- Files: create `docs/phase3/content-model/fields.md` and, in `docs/phase3/content-model.md`, turn the planned `fields.md` row into a link (work plan rule 3). Edit nothing else; no code, no fixtures under `docs/phase3/examples/` (P3-08 owns them), no edits to `docs/phase1/` or to `document.md`.
- Sources to cite, not restate: [page-config-v1.md](../phase1/page-config-v1.md) (the six v1 field properties, ID grammar, reserved `title` and `path`, form order rule), [config-validation.md](../phase1/config-validation.md) (first-error walk, error classes, JSON paths, canonical export) and `document.md` from P3-01a (type shape, upgrade rule).
- Field object: exactly `id`, `kind`, `label`, `help_text`, `required`, `order`, `group`, `multiple`, `validation`, in that schema order; all nine are required, as every v1 property is (closed shape, no defaults in the stored document). The first six keep their v1 types and rules. `group` is JSON `null` (ungrouped) or a string naming a group ID in the same type. `multiple` is a JSON boolean. `validation` is a JSON object; `{}` means no validation beyond the kind. This section states only that it is an object and links to `validation.md` (P3-01c) for its closed per-kind properties.
- Kinds: `kind` names one of the launch kinds from P3-02a to P3-02h: `short_text`, `long_text`, `rich_text`, `email`, `link`, `phone`, `integer`, `decimal`, `boolean`, `single_choice`, `multiple_choice`, `datetime`, `address`, `relationship`. A kind outside this list is `invalid_value` at `.kind`, as in phase 1. State that a parser accepts only the kinds implemented so far (P3-08 accepts `short_text` and `long_text`), rejecting the rest the same way.
- Cardinality: `multiple: true` on a kind that does not allow it is `invalid_value` at `.multiple`. A single-value field stores the kind's value shape; a multiple field stores a JSON array of that shape in entered order, `[]` when empty, and `required` then means at least one element. `multiple_choice` is multi-valued by kind and always has `multiple: false`; `single_choice` also has `multiple: false`. Kind contracts may add duplicate or count rules; this section adds none. The allowed-kind list is the open decision below.
- Group object: exactly `id`, `label`, `order`, in that schema order. `id` uses the phase 1 grammar; group IDs are unique within a type (`duplicate_id` at `$.content_types[N].groups[M].id`, later occurrence) in a namespace separate from field IDs, and `title` and `path` are not reserved for groups. `label` is a string (empty allowed). `order` is a positive integer unique among the type's groups (`duplicate_order`). A group with no fields is valid.
- Walk order: reuse the phase 1 first-error rule. Each field is checked in schema order, then field duplicate ID and order checks as in phase 1; then each group and group duplicates; then, in field-array order, a non-null `group` that names no group in the type is `invalid_value` at `$.content_types[N].fields[M].group`. A `group` string that fails the ID grammar is `invalid_id` there. Add no new error class.
- Layout: groups affect only form layout. Values stay keyed by field ID in `items.fields` and `snapshots.fields`; moving a field between groups or reordering never touches stored values. Field `order` stays unique across the whole type, grouped or not. The generated form (P3-20) shows ungrouped fields first in field order, then each group in group order with its label as a heading and its fields in field order; empty groups are omitted.
- Canonical export: fields sort by `order` then ID and groups by `order` then ID, following the phase 1 rule. Field and group properties use the schema orders above. `null` is written as `null`, and an empty `validation` object is exactly `{}` with no inner whitespace, like `[]`.
- v1 upgrade defaults, as required by P3-01a: `group: null`, `multiple: false`, `validation: {}`.
- Examples: one inline JSON type containing two groups (one empty), a grouped field, an ungrouped field and one `multiple: true` field, plus its canonical export bytes. Also give one invalid example per new rule: an unknown group reference, `multiple` on a disallowed kind, a duplicate group order and a missing `validation`, each with class, path and exit 3. Every block must parse with `python3 -m json.tool`.
- Acceptance: `bash scripts/test` stays green; every link resolves; the section defines all nine field properties, the group object, the multiple-allowed kind list, the walk order and error mapping, the layout rule, the canonical rules and the upgrade defaults. A reviewer can derive P3-08's field and group tests, and P3-18, P3-20 and P3-58 behaviour, without further design.
- **Open decision:** which kinds allow `multiple: true`. P3-58 names "text, link, email and relationship", and the PRD says "where that makes sense". Proposed set: `short_text`, `email`, `link`, `relationship`. Mark must confirm whether `long_text`, `rich_text`, `phone` and `datetime` (for example, repeating Event dates) also allow it. Blocks this ticket.

### P3-01c Content model contract: validation rules

Write the `validation` section: the closed set of validation properties per kind (text length bounds, numeric bounds and decimal places, choice options, relationship target types, link schemes) and the rule that unknown properties are errors.

**Guidance**

- Files: create `docs/phase3/content-model/validation.md` and, in `docs/phase3/content-model.md`, turn the planned `validation.md` row into a link (work plan rule 3). Edit nothing else. No code, no fixtures under `docs/phase3/examples/` (P3-08 owns them), and no edits to `docs/phase1/`, `document.md` or `fields.md`.
- Sources to cite, not restate: `fields.md` from P3-01b (the `validation` member is a JSON object, `{}` means nothing beyond the kind, and the multiple-allowed kinds), [config-validation.md](../phase1/config-validation.md) (first-error walk, JSON paths, error classes and exits, canonical export), [content-contract.md](../phase1/content-contract.md) section 9 error codes (`required`, `too_long`, 422) and the [ADR](../adr/0001-runtime-content-and-deployment.md) (tightening validation needs a preflight report, which P3-01d defines).
- Closed set per kind. All properties are optional unless marked required. A property not listed for the field's kind, including one that is valid for another kind, is `unknown_property` at `$.content_types[N].fields[M].validation.<name>`, exit 3. Use this schema order:
  - `short_text`, `long_text`: `min_length`, `max_length`. Both are positive JSON integers counting Unicode scalar values, as phase 1 does (`runeLength` in `internal/content/content.go`). `max_length` must not exceed the kind ceiling that stays in force: 255 for `short_text` (`MaxShortLength`) and 100000 for `long_text` (`MaxBodyLength`). Otherwise it is `invalid_value`.
  - `link`: `schemes`, a nonempty array of unique strings, each one of `http`, `https` or `mailto` (the P3-02c kind allowlist). It narrows the allowlist and cannot widen it. When absent, all three are allowed.
  - `integer`: `min`, `max`, JSON integers within int64. Negative values are allowed.
  - `decimal`: `places` (required), then `min` and `max`. `places` is a JSON integer from 0 to 9. `min` and `max` are JSON strings matching `^-?(0|[1-9][0-9]*)(\.[0-9]+)?$`, with at most `places` fraction digits and at most 18 digits in total, so a scaled value fits int64. P3-02d must use the same value grammar.
  - `single_choice`, `multiple_choice`: `options` (required), a nonempty array of objects with exactly `value` then `label`. `value` uses the phase 1 ID grammar (`invalid_id`) and is unique within the field (`duplicate_id` at `.options[K].value`, on the later occurrence). `label` is a nonempty string. Array order is display order.
  - `relationship`: `target_types` (required), a nonempty array of unique type IDs (`duplicate_id` on the later occurrence). Each ID must name a type in the same document, and a type may name itself.
  - `rich_text`, `email`, `phone`, `boolean`, `datetime`, `address`: no properties, so only `{}` is valid. Their fixed rules belong to the kind contracts (P3-02b to P3-02g).
- Cross-property rules: when both are present, `min_length` must not exceed `max_length`, and `min` must not exceed `max` (decimals are compared numerically). Equal values are allowed. A violation is `invalid_value` at the `max_length` or `max` path. There are no count properties (such as minimum or maximum items) for `multiple` fields in phase 3. On a `multiple: true` field, each property applies to each element.
- Walk order: `validation` is checked last among the field's members, after `kind`, following P3-01b. If `kind` is invalid, the walk has already stopped. Inside `validation`, apply the phase 1 order: required properties in schema order, then unknown properties in input order, then present values in schema order, then the cross-property rule, then duplicates in array order. A `target_types` entry that names no type is checked after the whole `content_types` walk, in type, field and entry order, and reported as `invalid_value` at `.validation.target_types[K]`. Add no new configuration error class.
- Canonical export: validation properties follow the schema orders above, and absent optional properties are omitted (never `null`). `options` keeps array order. `schemes` and `target_types` sort ascending, since they are sets. An empty object is exactly `{}`.
- Value error codes: this section names the value-side codes that the kind contracts and `internal/content/<kind>.go` tickets share, all 422 in the phase 1 error-page style. `too_short` for `min_length`, the existing `too_long` for `max_length`, `out_of_range` for `min`/`max`, `too_many_places` for `places`, `invalid_choice` for a value outside `options`, `scheme_not_allowed` for `schemes` and `target_type_not_allowed` for `target_types`. Give each property's meaning in one line. Kind contracts own parsing and empty-value rules.
- Direction for P3-01d: give each property one line saying what loosens it. Raising `max_length`/`max`, lowering `min_length`/`min`, removing a bound, adding a scheme, target type or option, and relabelling an option all loosen it. The reverse tightens it. Changing `places` or an option `value` counts as both. Leave the in-place and rejection rules to P3-01d.
- Examples: one inline valid JSON field per kind group above, plus the canonical export bytes for a `decimal` field and a `link` field with unsorted `schemes`. Add one invalid example for each rule: `min` on `short_text` (`unknown_property`), `max_length` 256 on `short_text`, `min` greater than `max`, a `decimal` missing `places` (`missing_property`), a duplicate option value, an unknown target type, and `{"x":1}` on `email`. For each, give the class, path and exit 3. Every block must parse with `python3 -m json.tool`.
- Acceptance: `bash scripts/test` stays green and every link resolves. The section defines the closed property set per kind, the ceilings, the cross-property rules, the walk order and error mapping, the canonical rules, the value error codes and the loosen/tighten direction. A reviewer can derive P3-08's validation-object tests, the kind validators (P3-45, P3-50 to P3-57) and the builder validation inputs (P3-48, P3-59) without further design.

Depends on: P3-01b.

### P3-01d Content model contract: allowed model changes

Write the `changes` section: which edits the field builder may apply in place (add field, add group, relabel, reorder, change help text, make optional, loosen validation) and which it rejects (remove populated field, change kind, change cardinality, tighten validation with non-compliant values). Reference the ADR; add the preflight report shape listing affected drafts and snapshots.

**Guidance**

- Files: create `docs/phase3/content-model/changes.md` and, in `docs/phase3/content-model.md`, turn the planned `changes.md` row into a link (work plan rule 3). Edit nothing else. No code, no fixtures under `docs/phase3/examples/`, and no edits to `docs/phase1/`, `document.md`, `fields.md` or `validation.md`.
- Sources to cite, not restate: the [ADR](../adr/0001-runtime-content-and-deployment.md) "Model changes" list (the rules this section makes precise), [content-contract.md](../phase1/content-contract.md) section 10 (snapshots record `type_id` and `config_revision`; populated fields cannot be removed, including fields used by retained snapshots; restore validates against the active definition), `fields.md` (P3-01b) and the loosen/tighten direction line per property in `validation.md` (P3-01c). Storage facts come from `internal/store/schema.sql`: working values in `items.fields`, history in immutable `snapshots.fields`, the live copy at `items.published_snapshot_id`, and `active_config.revision`.
- Input and matching: a change compares the active document with a complete proposed document. The proposed document must first pass the P3-08 validation walk (configuration errors, exit 3); classification runs only on a valid document. Types match by type ID, fields by field ID within a type, groups by group ID and options by option `value`. IDs never change in place. A changed ID is a removal plus an addition, and each is classified on its own.
- Allowed in place, with no value scan and no stored row touched: add a type; add an optional field; add, relabel, reorder or remove a group; move a field between groups or out of one; change a type's `label` or `plural_label`; change a field's `label`, `help_text` or `order`; set `required` from true to false; any validation change that `validation.md` marks as loosening only; relabel or reorder choice options.
- Allowed after a value scan (the preflight): set `required` from false to true; add a required field; any validation change marked tightening or both (including a `places` change, removing an option, scheme or target type, raising `min_length`/`min` or lowering `max_length`/`max`); remove a field; remove a type. The change applies only if the scan finds no affected row. Otherwise the whole proposal is rejected with the preflight report, nothing is written and `active_config.revision` is unchanged.
- Always rejected, with no scan: changing a field's `kind`; changing a field's `multiple`. A kind change is never fixed by conversion (ADR: no implicit coercion or truncation).
- Scan scope, per the ADR: required and validation checks scan every working draft of the type (`items.fields`) and every published snapshot (the row at `items.published_snapshot_id`). Unpublished historical snapshots are not scanned for these checks, because restore revalidates them later (P3-03). Field removal scans every draft and every retained snapshot of the type, published or not. A value there, even in old history, blocks removal. Type removal is blocked by any `items` row of that type. Phase 3 has no Trash, so this covers every item. Phase 5 must count trashed items as ordinary rows.
- Check rules: "empty" is an absent key or the kind's empty value from its kind contract. For phase 1 text, that is a whitespace-only string, as in the `required` check in `internal/content/content.go`. A `multiple` field is empty when it is `[]`. A required check flags every empty value. A validation check runs the proposed field's kind validator on each non-empty value, and on each element for `multiple`. The report uses the value error code from `validation.md` (`too_short`, `too_long`, `out_of_range`, `too_many_places`, `invalid_choice`, `scheme_not_allowed`, `target_type_not_allowed`). `target_type_not_allowed` looks up the stored target item's `type_id`. Adding a required field to a type that has any item always fails, because no stored value exists. Say so, and give the supported sequence: add it as optional, fill the values, then make it required. The reviewed-migration path in the ADR is not in phase 3.
- Report shape: define one JSON-shaped result that P3-12 returns, P3-17 renders and phase 6 deploy can reuse. The result has `result` (`allowed` or `rejected`), then `changes`, the classified change list, each entry with `change` (a code from a closed list the section defines, such as `field_added` or `field_required_set`), `type_id`, `field_id` or `group_id` when applicable, and `path` (JSON path in the proposed document). It also has `rejections`, where each entry has `code`, `type_id`, `field_id`, `path` and `affected`. `affected` is an array of rows. Each row has `owner_kind` (`draft` or `snapshot`), `item_id`, `title`, `snapshot_id` and `seq` (snapshot only, otherwise omitted), and `value_code` (`required` or a value error code). Also include `affected_count`. Rejection codes form a closed list: `kind_changed`, `cardinality_changed`, `field_populated`, `type_populated`, `values_noncompliant`. Order is deterministic: rejections in proposed-document walk order (removals in active-document order, after the proposed walk), and affected rows by `item_id` with the draft before its snapshots in `seq` order. The report carries every affected row. Display limits belong to P3-17.
- Apply rule: the scan and the configuration write run in one write transaction. The write stores the proposed document and increments `active_config.revision` by one. No `items` or `snapshots` row is changed. The builder form carries the revision it loaded. A mismatch at apply time is refused, in the style of the phase 1 `stale_draft` 409. Name it `stale_config`, give its wording, and never merge. Builder rejections return 422 with the report, keeping the submitted form input, as in phase 1. The production refusal belongs to P3-07.
- Out of scope: retaining prior configuration revisions for snapshot inspection (P3-03), per-kind empty and value rules (P3-02a to P3-02h), and deploy or diff commands (phase 6). Link to those tickets. Do not define them here.
- Examples: give one worked case per class. Include a relabel (allowed), a make-required with one empty draft (rejected, with a full report), a `max_length` cut from 255 to 10 against one long published snapshot (rejected), removal of a field used only by an old unpublished snapshot (rejected `field_populated`), a kind change (rejected, no scan) and removal of an empty field (allowed). Every JSON block must parse with `python3 -m json.tool`.
- Acceptance: `bash scripts/test` stays green and every link resolves. The section defines the matching rule, the three classes with every property from P3-01b and P3-01c placed in exactly one class (or in both loosen and tighten directions), the scan scope, the empty and check rules, the closed change and rejection code lists, the report shape and ordering, and the apply and stale rules. A reviewer can derive P3-12's table of allowed and rejected transformations, and the P3-17 preflight rejection, without further design.

Depends on: P3-01c.

### P3-02a Field kind contract: text and email

Create `docs/phase3/field-kinds.md` as an index linking section files under `docs/phase3/field-kinds/`. Write the section for `short_text`, `long_text` and `email`: stored JSON value shape, empty-value rule, validation, form control and public rendering.

**Guidance**

- Files: create `docs/phase3/field-kinds.md` (index) and `docs/phase3/field-kinds/text-and-email.md` (section). The index has one table row per section file, with `text-and-email.md` linked. List the other rows unlinked as "planned", since each later ticket adds its own link (work plan rule 3): `rich-text.md` (P3-02b), `link-and-phone.md` (P3-02c), `numbers-and-boolean.md` (P3-02d), `choice.md` (P3-02e), `datetime.md` (P3-02f), `address.md` (P3-02g) and `relationship.md` (P3-02h). Edit nothing else. No code, no fixtures under `docs/phase3/examples/`, and no edits to `docs/phase1/` or `docs/phase3/content-model/`.
- Sources to cite, not restate: [content-contract.md](../phase1/content-contract.md) section 5 (body rules) and section 9 (`required`, `too_long`, 422), [config-validation.md](../phase1/config-validation.md) (code-point counting, 255 limit), `fields.md` (P3-01b: `multiple`, the multiple-allowed kinds, value storage) and `validation.md` (P3-01c: `min_length`/`max_length`, ceilings, shared value codes). The current behaviour lives in `PreparePageDraft` and `ValidateStoredPageDraft` in `internal/content/content.go`, `internal/render/page.html` and `internal/web/admin_form.html`.
- The index also fixes the shared rules and the section template that P3-02b to P3-02h copy. Each kind gets these subsections, in order: Stored value, Empty value, Input normalization, Checks and error codes (in check order), Stored-value recheck, Form control, Public rendering, Multiple values. Shared rules:
  - Values are keyed by field ID in `items.fields` and `snapshots.fields`. A save writes a key for every field in the type.
  - A missing key, such as a field added after the item was saved (P3-14), reads as the kind's empty value and is not an error.
  - Each field reports at most one error code per save, the first failing check in the kind's check order.
  - An empty optional value skips every check after the empty test, including `min_length`.
  - Public rendering escapes values through `html/template` and omits a field's `<section>` when its value is empty. The theme shows no field labels, matching phase 1.
  - For a `multiple` field (only the kinds P3-01b allows), blank entries are dropped before the checks run, and each remaining element is checked on its own. Errors are reported on the field. The value renders as `<ul>` with one `<li>` per element in stored order, using the kind's single-value markup inside.
- `short_text` and `long_text` keep phase 1 behaviour byte for byte, so existing Page sites and the P3-39 registration need no data change. State that:
  - The stored value is a JSON string, stored as submitted with no trimming or Unicode normalization. `long_text` alone converts `\r\n` and `\r` to `\n`.
  - The empty value is `""`. A value is empty when `strings.TrimSpace` gives `""`, so a whitespace-only value fails `required`. An optional whitespace-only value is stored as is.
  - Checks, in order: `required`, then the ceiling or `max_length` (`too_long`), then `min_length` (`too_short`). All counts are Unicode code points after newline normalization. Phase 3 adds no control-character or newline check to either kind, because that would tighten stored data.

- What is cached (P3-35): only `200` bodies of the public item route, keyed by `(generation, path)`, where `path` is `r.URL.Path` after the existing alias rejection (query strings are ignored, as the phase 1 route already ignores them). - Bound and eviction (P3-35): `internal/render/cache.go` exposes `NewCache(maxBytes, maxEntryBytes int)` and defaults `DefaultMaxBytes = 32 << 20` and `DefaultMaxEntryBytes = 1 << 20`. The cache remembers the newest generation it has seen; `Get` or `Put` with a newer generation drops every older entry at once, and `Put` with an older generation is a no-op. Safe for concurrent use (one mutex; tests run under `go test -race`). `Stats()` returns hits, misses, entries and bytes for tests; no public response header exposes cache state. State that the defaults are tuned later by the phase 6 load runs, not in phase 3.

The body is served either way, since it was correct when the request began.
