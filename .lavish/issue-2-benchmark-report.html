Why the scores differ

B · Complete, but oversized

Every major contract decision and prescribed scenario is present, with excellent executable-test ownership. Its 555 lines, optional alternatives, and low-level DSN detail violate the request for compactness.

D · Implementation-ready, but slower

Strong constraints, typed operations, transaction rules, and failure cases. It reaches the same quality as B with 18.8% more time and 15.1% more tokens.

A · Compact and balanced

All eight scenarios are covered with good atomicity and version rules. UUID generation is not fully pinned and the CLI synopsis omits --apply.

E · Qualifies with a data-portability risk

Fixed seed UUIDs across sites would collide during future import or restore. Draft lifecycle and server-rendered route coverage also need correction.

C · Incomplete handoff

Scenario coverage is decent, but concrete repository operations are absent. Its seed command and response design pull away from the agreed product direction.

F · Too many open decisions

Versions, seed data, serve flags, identifier formats, timestamps, and current-versus-future responsibilities remain unresolved. P1-03 would still need architecture work.

Efficiency evidence

Same model, different profile

  • B beat D on time by 18.8% and tokens by 15.1%, with equal quality. Both used Opus 5.5.
  • A beat C on time by 34.5%, tokens by 20.3%, and reported cost by 16.1%. Both used Luna 5.6.
  • Profile instructions and run behavior mattered enough to change whether the ticket passed.
Limits

What this batch cannot prove

  • One run per candidate does not establish stable model averages.
  • One blind reviewer leaves scoring variance unmeasured.
  • Claude interactive transcripts contain no session-level dollar cost.
  • Repository checks passed for all candidates but do not validate contract semantics.
